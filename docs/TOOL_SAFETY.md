# Tool Safety and Execution Controls Documentation

This document outlines the security architecture, safety boundaries, and defensive controls implemented in the FastAPI tool-calling RAG application. These measures ensure robust, secure, and predictable interactions between the Google Gemini model and backend tools.

---

## Core Security Controls

### 1. Centralized Tool Registry (White-listing)
* **Rule:** Tool names must be checked against the registry.
* **Implementation:** The application maintains a centralized `tool_registry` dictionary. The Gemini model cannot execute arbitrary functions; every tool call requested by the model must match an explicit, pre-registered function name. Any unknown tool name is immediately rejected.

### 2. Strict Argument Validation
* **Rule:** Tool arguments must be validated.
* **Implementation:** All inputs passed to backend tools are strictly validated using Pydantic models (e.g., `DateTimeInput`, `CalculatorInput`). Invalid types, missing fields, or out-of-bound parameters fail validation before execution occurs.

### 3. Rejection of Invalid Calls
* **Rule:** Invalid tool calls must not execute.
* **Implementation:** If tool arguments fail validation or an unknown tool is invoked, the execution boundary intercepts the failure, returns a structured error response to the model (`{"success": False, "error": "..."}`), and prevents execution.

### 4. Maximum Round Limit Protection
* **Rule:** Tool execution must have a maximum round limit.
* **Implementation:** Multi-turn tool execution loops enforce a strict threshold (`max_rounds=5`). This prevents infinite conversational tool-calling loops and protects against resource exhaustion.

### 5. Sanitized Error Handling
* **Rule:** Errors must not expose secrets or stack traces to users.
* **Implementation:** Internal Python exceptions and stack traces are caught at the service boundary. Clients and models receive clean, human-readable, and sanitized error messages without revealing system internals, file paths, or API keys.

### 6. Ban on Arbitrary Code Execution
* **Rule:** The application must not execute arbitrary shell commands or Python code generated by the model.
* **Implementation:** The model is strictly restricted to calling predefined Python functions registered in the codebase. Dynamic code evaluation (`eval`, `exec`) and OS shell access (`subprocess`) are completely banned.

### 7. Data Boundary for Tool Outputs
* **Rule:** Tool outputs must be treated as data, not trusted instructions.
* **Implementation:** Outputs returned by tools (such as database search results or calculation numbers) are structured as JSON data payloads. They are fed back to the model as context data (`role="user"` format) rather than executed as system instructions, mitigating indirect prompt injection risks.

### 8. Secure Logging Practices
* **Rule:** Tool execution must be logged without logging credentials or sensitive content unnecessarily.
* **Implementation:** Audit logs record tool names, execution status, and timestamps. Sensitive values such as API keys, authorization tokens, or private user queries are excluded from standard logging outputs.

### 9. Safe Calculator Implementation
* **Rule:** The calculator must not evaluate arbitrary expressions.
* **Implementation:** The `calculate` tool uses explicit Python arithmetic operators (`+`, `-`, `*`, `/`) based on validated operands rather than parsing or evaluating raw string expressions.

### 10. Robust Handling of Repeated or Malformed Calls
* **Rule:** The application must handle repeated or malformed tool calls safely.
* **Implementation:** The tool-calling service gracefully handles malformed arguments, duplicate tool requests, and recursive invocation attempts by returning standardized error payloads.

---

## System Scope & Side-Effect Boundaries
For this application, **all registered tools (`calculate`, `get_current_datetime`, and `search_knowledge_base`) are strictly read-only** with respect to external systems. 
* No tools exist that can send emails, delete records, make financial purchases, or modify production databases.
* All data flows are contained within local state and read-only vector/document indices.
