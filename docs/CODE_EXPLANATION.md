# Code & System Architecture Explanation

This document provides a conceptual overview and technical breakdown of the key principles powering the Semantic Document Search API.

---

## 1. Difference Between an Embedding and an LLM Response

* **Vector Embedding:** A numerical representation of text formatted as a fixed-length array of floating-point numbers (e.g., 768 or 1536 floats). It captures the semantic meaning, context, and relationships of the input text in a high-dimensional vector space. Embeddings are non-human-readable data points used for mathematical comparisons like clustering and vector search.
* **LLM Response:** Natural language text output generated autoregressively by a large language model (e.g., Gemini, GPT-4) based on a prompt. It is human-readable, conversational, and synthesized directly from model weights or provided context.

---

## 2. Why Both Documents and Queries are Converted into Vectors

Computers cannot natively calculate semantic similarity from raw text strings without relying on exact keyword matching. By projecting both documents and search queries into the same high-dimensional vector space:
* Words with similar meanings (e.g., "automobile" and "car") are placed close to each other.
* The system can evaluate mathematical proximity rather than relying on exact lexical overlap.
* Free-form search queries can be directly mapped against static document indexes to find the closest semantic neighbors.

---

## 3. How Cosine Similarity Helps Rank Documents

Cosine similarity measures the cosine of the angle between two multi-dimensional vectors in a vector space using the dot product normalized by their magnitudes:

$$\text{Similarity}(A, B) = \frac{A \cdot B}{\|A\| \|B\|}$$

* **Direction over Magnitude:** Unlike Euclidean distance, cosine similarity measures direction rather than magnitude, ensuring longer documents are not penalized or artificially boosted simply due to length.
* **Ranking Mechanics:** A cosine similarity value near $1.0$ indicates that the document vector and query vector point in nearly the same direction (high semantic alignment). Sorting these values in descending order yields the final relevance ranking.

---

## 4. Why Document and Query Embeddings Must Be Compatible

For similarity math (like dot product or cosine distance) to be valid, both vectors **must** share the exact same embedding space:
* **Identical Dimensions:** A 768-dimensional query vector cannot be mathematically compared with a 1536-dimensional document vector.
* **Identical Feature Space:** Embeddings must be produced by the same underlying model version (e.g., `text-embedding-004`). Vectors generated by different models project concepts into completely different feature spaces, making cross-model comparisons meaningless.

---

## 5. What Determines the Final Search Ranking

The final search ranking is determined by:
1. **Cosine Similarity Score:** The scalar similarity score calculated between the query vector and each stored document embedding.
2. **Sorting Order:** Ordering candidates in descending order based on their similarity score.
3. **Top-K Cutoff:** Truncating the sorted list to return only the highest $K$ results requested by the user.

---

## 6. What Happens When a New Document is Added

When a new document is posted to the API:
1. **Validation:** The request payload is checked against Pydantic schemas (validating unique ID, title, and content).
2. **Embedding Generation:** The document content is sent to Google's GenAI API (`text-embedding-004`) to generate its vector embedding.
3. **In-Memory Storage:** The raw document metadata is appended to `search_service.documents`, and its vector is stored in `search_service.document_embeddings`.
4. **Immediate Availability:** The document becomes searchable in all subsequent search calls.

---

## 7. Why a Semantically Relevant Document Might Rank Poorly

* **Granular vs. Global Meaning:** If a document is very long and covers many topics, its overall vector embedding becomes averaged out, diluting the specific passage relevant to the query.
* **Embedding Model Domain Nuances:** Specialized domain jargon (e.g., niche legal or medical terminology) might not be strongly represented in a general-purpose embedding model.
* **Shorter Query Ambiguity:** Extremely short or ambiguous queries may yield a query vector that aligns closely with general content rather than specific target documents.

---

## 8. Why Similarity Score is Not Necessarily a Probability

Cosine similarity scores range from $-1.0$ to $1.0$ (or $0.0$ to $1.0$ for non-negative embeddings):
* **Not Normalized Probabilities:** These scores do not satisfy probability axioms—the sum of similarity scores across all documents in an index does not equal $1.0$.
* **Relative Metric:** A similarity score of $0.85$ does not mean there is an 85% probability that the document is correct; it simply indicates high directional alignment in vector space compared to lower-scoring candidates.

---

## 9. Handling 1 Million Documents Instead of 20

To scale from an in-memory list of 20 documents to a production dataset of 1,000,000+ documents:
* **Dedicated Vector Database:** Replace in-memory lists with specialized vector search engines such as Qdrant, Milvus, Pinecone, or PGVector.
* **ANN (Approximate Nearest Neighbors):** Use vector indexing algorithms like **HNSW (Hierarchical Navigable Small World)** or **IVF (Inverted File Index)** instead of brute-force linear comparisons ($O(N)$).
* **Chunking Strategy:** Split long documents into smaller semantic chunks (e.g., 256–512 tokens) with overlap before embedding.
* **Asynchronous Indexing:** Process document additions and embedding generation asynchronously using background workers and message queues (e.g., Celery, Redis).

---

## 10. Difference Between This Search Engine and a RAG Application

* **This Search Engine:** Performs **Retrieval** only. It takes a query, converts it to an embedding, retrieves the most similar documents based on vector distance, and returns raw document metadata and similarity scores to the user.
* **RAG (Retrieval-Augmented Generation) Application:** Combines **Retrieval** with **Generation**. It takes the top retrieved documents from a search engine, injects them into an augmented prompt as context, and passes them to an LLM (like Gemini or GPT-4) to synthesize a coherent, human-readable answer that directly answers the query.
